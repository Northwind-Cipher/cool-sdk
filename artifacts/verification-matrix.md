## Notes and caveats (read before citing this matrix externally)

- **"Consistency" is not a distinct field in `verifyReceiptV2`'s verdict.** The codebase's own
  7-domain vocabulary is `binding, signature, inclusion, witnesses, attestation, enclave, anchor`
  (see `domainOrder()` in `src/phala/verify.ts`). RFC 6962 consistency proofs are implemented and
  tested (`src/merkle.ts`, `consistencyProof`/`verifyConsistency`) but exercised as a log operation,
  not surfaced as its own verdict domain. This validation confirms consistency is real by pointing
  to that implementation and its passing test, not by inventing a verdict field that doesn't exist
  in the current API.
- **Witness independence, honestly stated**: the witness cosignature in this validation was
  produced by a keypair generated by the same operator running this validation (me), standing in
  for a genuinely separate third party. The cryptography is 100% real — a distinct keypair,
  independent of the enclave-sealed signing key, signing the exact bytes the transparency log
  signed, counted only because `external: true` and a real hybrid-signature check passes. What is
  *not* yet demonstrated is operational independence — a different organization or operator running
  that witness key. Production deployment would put the second key under a separate party's control.
- **Attestation "pass" vs. "hardware"**: `attestation: pass` here means the quote's chain to a
  vendor root (Intel, via Phala Cloud's DCAP-backed API) was checked and returned `verified: true`,
  live, at verification time. This is real hardware attestation, not "hardware mode" reported
  optimistically — the verifier code structurally cannot reach `pass` without a configured verifier
  actually returning `ok: true` (see `src/phala/verify.ts: verifyAttestationDomain`).
- **Docker image digest != TDX measurement** — kept distinct throughout. MRTD/RTMR0-2 (base
  firmware/kernel/kernel-cmdline) were IDENTICAL between Deployment A and B; only RTMR3 (the
  application/compose-identity register) changed, which is the theoretically correct TDX behavior
  for an application-level code change with the same base OS image. See
  `artifacts/final-evidence/measurement-change-*.json`.
